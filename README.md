# proxycheck — чекер и клиент публичных Shadowsocks-прокси

Одна программа, два режима:
- **Без аргументов** → GUI (таблица серверов, вкладка закладок, чекбоксы
  выбора, старт/стоп прокси, замер скорости ↓/↑, выходной IP, локальный
  DNS, вкладка логов, трей, своя иконка, сортировка по столбцам).
- **С аргументами** → консольная утилита для скриптов автоматизации.

## Этот этап — нашёл серьёзный баг с чекбоксами

**Пункт 3 оказался корнем и пункта 1 тоже.** При скролле таблицы Fyne
переиспользует один и тот же виджет чекбокса для разных строк
(виртуализация — иначе тысячи строк рендерились бы разом). А
`widget.Check.SetChecked()` в Fyne вызывает `OnChanged`, если новое
значение отличается от текущего внутреннего состояния виджета. Мы
сначала звали `SetChecked(r.selected)`, а только потом переназначали
`OnChanged` — то есть в момент `SetChecked` ещё был жив СТАРЫЙ колбэк,
привязанный к предыдущей строке, которая использовала этот же виджет.
Он получал значение НОВОЙ строки и молча записывал его в чужую
`.selected`. При скролле это выглядело как случайный сброс/подстановка
галочек — и именно поэтому «Замер скорости отмеченных» вдруг измерял
весь список: часть строк оказались отмечены не пользователем, а этим
багом.

Тот же баг был и у поля комментария в закладках (`Entry.SetText` по
той же причине вызывает `OnChanged`).

**Исправил везде** — теперь порядок строго: сначала обнуляем колбэк,
потом меняем значение виджета, потом вешаем новый колбэк. Написал тест
на настоящем виджете Fyne (`TestCheckboxReuseDoesNotCorruptOtherRow`),
который прогоняет ровно этот сценарий переиспользования — и
контрольный тест, подтверждающий, что баг действительно воспроизводится
при старом (неправильном) порядке операций.

**Остальное:**
2. Колонку **IP** расширил — полные IPv4-адреса теперь не обрезаются.
4. Клик по заголовку **«Прокси»** теперь сортирует по запущенности.
   Плюс запущенные прокси теперь всегда закреплены сверху (вторым
   уровнем после отмеченных галочкой) — как и просил.
5. **Скорость теперь сохраняется между запусками** — до этого в
   settings.json попадали только IP/статус/задержка, но не скорость.
   Добавил персистентность (и для успешных замеров, и для неудачных
   попыток — чтобы отличие "не мерили"/"не вышло" тоже не терялось).
   Проверил тестом полного цикла сохранение→загрузка.
6. **Про подозрительно низкую скорость отдачи** — нашёл вероятную
   методическую проблему: тест upload гонял всего 2 МБ против 5 МБ на
   download. При типичной для этих серверов задержке 300-500ms
   маленький объём во многом уходит на разгон TCP (slow start) и не
   успевает показать реальную устоявшуюся скорость — отсюда
   заниженные числа. Уравнял объём с download (5 МБ). Важная честная
   оговорка: я не могу проверить реальные цифры на живых серверах из
   своей песочницы — это обоснованная теория, а не стопроцентно
   подтверждённый факт. Также вероятно, что бесплатные/публичные
   прокси реально ограничивают исходящий канал сильнее входящего
   (частая практика против злоупотреблений) — так что после фикса
   числа могут вырасти, но не обязательно сравняются со скачиванием.

- Три состояния статуса (жив/мёртв/умер) + умная перепроверка при
  старте с проверкой интернета.
- Починил `DetectExitIP` — читает по Content-Length, а не до EOF.
- 7 фич: старт свёрнутым, выходной IP, скорость ↓/↑, локальный DNS,
  закладки с комментариями, вкладко-зависимые кнопки, флаг `--debug`.
- Фильтрация неподдерживаемых методов, глубокая проверка через TLS.
- Зомби-процессы: single-instance замок, SO_EXCLUSIVEADDRUSE.
- SOCKS5 Grant/Deny по факту, слушаем `0.0.0.0`, автоправило файрвола.

1. **Длинные домены больше не заезжают на соседнюю колонку.** Вместо
   того чтобы гадать с прокруткой внутри ячейки (это в Fyne непросто и
   плохо сочетается с таблицей), включил стандартное усечение текста
   многоточием (`…`) — сам текст в данных не обрезается, только
   отображение. Плюс саму колонку «Адрес:порт» немного расширил.
   Усечение включил не только там, а на все текстовые ячейки в обеих
   таблицах — на будущее, от таких же сюрпризов в других колонках.
2. **Различаю «не проверялось» и «не получилось».** Раньше и то, и
   другое показывалось одинаковым «—», из-за чего было не понять, то
   ли для этого сервера ещё не дошла очередь, то ли замер/резолв
   реально провалился. Теперь если попытка была и не вышла — пишет
   «ошибка», а не молчаливый прочерк. Заодно частично объясняет то,
   что было на скриншоте: замер скорости идёт последовательно по
   списку, и «—» у серверов в конце — это, возможно, было просто «ещё
   не дошли», а не «не работает» (скриншот делается в моменте, пока
   фон продолжает считать).
3. **Клик по иконке в трее теперь сразу открывает окно** — через
   `SetSystemTrayWindow` (API появился в Fyne 2.7). Раньше приходилось
   лезть в меню правой кнопкой.

визуальное подтверждение — за тобой.

## Этот этап — три состояния статуса + умная перепроверка при старте

По твоей просьбе (и, скорее всего, каша с IP на скриншоте — это как раз
устаревшие данные ДО фикса `DetectExitIP`, а не новый баг):

**Три состояния вместо двух.** Раньше был просто "жив"/"мёртв" — теперь:
- **«жив»** — прошёл проверку сейчас.
- **«мёртв»** — проверен и никогда не отвечал.
- **«умер»** — раньше отвечал, сейчас перестал. Это и есть та самая
  видимость деградации, которую ты просил.

Обычный массовый скан («Загрузить и проверить») по-прежнему выбрасывает
мёртвые сервера из таблицы — иначе список из публичных источников
захламляется тысячами шумных записей, как договорились раньше. А вот
**"важные" сервера — уже запущенные, в закладках, отмеченные галочкой —
теперь не пропадают**, даже если умерли: остаются в таблице со статусом
«умер», чтобы это было видно.

**Умная перепроверка при запуске программы.** Именно то, что ты описал:
1. Программа стартует, восстанавливает прошлую сессию.
2. Сначала — прямая проверка интернета (без прокси, просто TCP до
   Cloudflare) — если своего интернета нет, важные сервера НЕ
   помечаются "умер" зря (это нечестно по отношению к ним — может, дело
   не в них, а в том, что Wi-Fi ещё не подключился).
3. Если интернет есть — перепроверяет все важные сервера с прошлой
   сессии реальным подключением, обновляет статусы (включая переход в
   "умер") и выходной IP.
4. Сохранённые активные прокси запускаются независимо от результата
   проверки интернета — им сеть для самого запуска (bind локального
   порта) не нужна.

**Проверка перед замером скорости.** Тоже сделал, как предлагал: прежде
чем гонять полноценный замер скорости (что реально долго при таймауте),
сначала быстрая проверка живости. Если сервер не отвечает — статус сразу
обновляется на "умер"/"мёртв", замер для него пропускается, идём дальше
по списку, а не ждём таймаута скачивания впустую.

### Как протестировано

Логику переходов статусов (`жив→умер`, `важный мёртвый остаётся`,
`неважный мёртвый выбрасывается`) прогнал через прицельные юнit-тесты
(`TestNextStatusTransitions`, `TestSetFromResults_ImportantServerSurvivesAsDied`
и другие) — не требуют сети вообще, чистая логика. Полный сценарий
восстановления с недоступным сервером проверил под виртуальным
дисплеем: сохранил `settings.json` с "живым" отмеченным сервером,
указывающим в никуда, запустил — итоговый файл настроек показал
`status: "died"` именно там, где и должен был. Работает end-to-end.

**Иконка** тоже на месте — добавил из твоего .ico и в сам `.exe` (через
Windows resource), и в приложении (окно/трей через Fyne).

## Про переход на xray-core / другие протоколы (VLESS/VMess/Trojan/Hysteria/WireGuard)

Обсуждали отдельно: полноценный xray-core здесь я подключить не берусь
— гигантское дерево зависимостей, в моей песочнице с её ограничениями
сети это почти гарантированно утонет в бесконечных ручных обходах.
Дальше по своим протоколам — двигаемся по одному, начиная с того, что
реально написать самому (Trojan сильно проще VLESS/VMess). Hysteria и
WireGuard — UDP/QUIC поверх другой транспортной модели, совсем другой
масштаб работы; отдельный самостоятельный этап, если вообще понадобится.

## Файл настроек (settings.json)

Лежит рядом с исполняемым файлом. Хранит `last_scan_servers`,
`profiles` (активные на момент закрытия прокси), `default_health_interval_sec`,
`start_port`. Сохраняется автоматически при изменениях. Можно смело
удалить — программа начнёт с чистого состояния.

## Использование CLI

```bash
./proxycheck -h                                    # все флаги
./proxycheck --list-sources                         # источники серверов
./proxycheck -o proxies.json -c 100 -t 5             # обычный скан (TCP + глубокая проверка)
./proxycheck -o proxies.json -deep-verify=false      # только быстрый TCP, без глубокой проверки
./proxycheck -o proxies.json -sequential -top 10     # топ-10, последовательно
./proxycheck -o proxies.json -select "1.2.3.4:8388,5.6.7.8:8388"
./proxycheck -top 5 -speedtest                       # разовый замер скорости
./proxycheck -top 3 -serve -health-interval 15 -fail-threshold 2  # демон
```

## Использование GUI

- «Загрузить и проверить» — качает списки, TCP-скан, затем (если включена
  «Глубокая проверка») реальное подключение к каждому прошедшему TCP —
  в списке остаются только реально рабочие сервера.
- Галочка ✓ — отметить для экспорта/замера скорости.
- «Старт»/«Стоп» в строке — поднимает/останавливает локальный SOCKS5
  именно на этот сервер (слушает на всех интерфейсах — 0.0.0.0).
- «Экспорт всех рабочих» / «Экспорт отмеченных ✓» — сохранение в JSON.
- «Замер скорости отмеченных ✓» — качает тестовый файл через каждый.
- «Авто-мониторинг активных» + «Интервал проверки (сек)» — периодическая
  проверка запущенных прокси, при падении — точечный failover.
- «Стартовый порт» — с какого порта начинать назначать новым прокси.
- Вкладка «Логи» — все события в реальном времени.
- «Свернуть в трей» / «Выход» — явные кнопки, не только в трее.
- При следующем запуске программа сама проверяет, не запущена ли уже, и
  восстанавливает прошлую сессию автоматически.

```
│   ├── settings/             — персистентность настроек/профилей (settings.json)
```

## Важная оговорка про здоровье и тестирование

Всё ядро (шифрование, SOCKS5, релей, health-loop, замер скорости)
покрыто end-to-end юнит-тестами — я прогнал их у себя: полный путь
клиент→SOCKS5→AEAD-шифрование→сервер→эхо/HTTP работает и с многочанковыми
данными (>16KB), и с failover, и с реальным замером скорости через
`httptest`-сервер. Живые публичные прокси через реальный интернет я
здесь проверить не могу (сеть в моей песочнице ограничена белым
списком доменов) — так что первый прогон на реальных серверах лучше
сделать у себя и сказать, если что-то не так.

## Сборка

### Windows — уже собрано, см. приложенный `.exe`

Если захочешь пересобрать сам:

```bash
CGO_ENABLED=1 GOOS=windows GOARCH=amd64 CC=x86_64-w64-mingw32-gcc \
  go build -ldflags="-s -w" -o proxycheck.exe .
```

### Raspberry Pi (Debian arm64) — GUI

**Кросс-компиляция GUI под ARM64 у меня не получилась** — Fyne использует
cgo и тянет системные X11/OpenGL библиотеки под ARM64, а они лежат на
`ports.ubuntu.com`, которого нет в разрешённом списке доменов моей
песочницы (только `archive.ubuntu.com`, а там только amd64-пакеты).
Проверил несколько путей обхода — все требуют либо ARM64-sysroot с этого
домена, либо стороннего WAN-ресурса (SourceForge и т.п.), тоже недоступного.

**Решение**: собери GUI прямо на самой Pi — там эти библиотеки ставятся
через обычный `apt` одной командой, никакой кросс-компиляции не нужно.
Я приложил готовый скрипт `build-on-pi.sh` — просто:
```bash
chmod +x build-on-pi.sh
./build-on-pi.sh
```
Это установит зависимости и соберёт `./proxycheck` за несколько минут
(Go на Pi 4/5 компилирует не очень быстро, наберись терпения на первый раз).

### Raspberry Pi — CLI без GUI (уже собрано)

Я собрал `proxycheck-arm64-cli` здесь — это CLI-only сборка (тег `nogui`,
`CGO_ENABLED=0`, статический бинарник, без cgo-зависимостей вообще).
GUI-режим в ней не работает (покажет сообщение и выйдет) — используй
`-h` и остальные CLI-флаги, как обычно. Если нужен именно GUI на Pi —
собери `build-on-pi.sh`.

## Использование CLI

```bash
./proxycheck -h                                    # все флаги
./proxycheck --list-sources                         # источники серверов

# обычный скан + сохранение всех живых
./proxycheck -o proxies.json -c 100 -t 5

# только топ-10 самых быстрых, последовательная проверка
./proxycheck -o proxies.json -sequential -top 10

# сохранить только конкретные сервера
./proxycheck -o proxies.json -select "1.2.3.4:8388,5.6.7.8:8388"

# замер скорости отобранных (без -serve — разово, выводит в консоль)
./proxycheck -top 5 -speedtest

# демон: поднять прокси на топ-3, авто health-check каждые 15с,
# при 2 неудачных подряд проверках — точечный failover
./proxycheck -top 3 -serve -health-interval 15 -fail-threshold 2
# локальные порты: 127.0.0.1:1080, 1081, 1082 — Ctrl+C для остановки
```

Полный список флагов — `./proxycheck -h`.

## Использование GUI

- «Загрузить и проверить» — качает списки, чекает все сервера
  (параллельно/последовательно — чекбокс, число потоков и таймаут — поля рядом).
- Галочка ✓ в первой колонке — отметить сервер для экспорта/замера скорости.
- Кнопка «Старт» в строке сервера — поднимает локальный SOCKS5-порт
  именно на этот сервер (следующий свободный порт от 1080).
- «Экспорт всех рабочих» / «Экспорт отмеченных ✓» — сохранение в JSON
  (формат shadowsocks-rust).
- «Замер скорости отмеченных ✓» — по очереди поднимает временный
  туннель на каждый отмеченный сервер и качает тестовый файл.
- «Авто-мониторинг активных» (включено по умолчанию) — периодически
  проверяет запущенные прокси и при падении подменяет на живой из
  резервного пула (без полного пересканирования).
- Закрытие окна сворачивает в трей (не завершает работу активных
  прокси) — есть иконка в трее с меню.
- Флаги при запуске: `proxycheck -gui-autostart` (сразу загрузить+
  проверить при старте) и `proxycheck -gui-tray` (сразу свернуться,
  подразумевает autostart).
